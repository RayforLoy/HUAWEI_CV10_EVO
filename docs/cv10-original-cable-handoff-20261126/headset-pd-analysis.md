# 原厂线掉线时，头显固件执行了什么

测试的头显版本为 `CV10AC10.0.1.357`。以下偏移均从升级工具内完整的 `Dfu/halliday.dfu` 开头计，SHA-256 为 `85579969f7362cc9acf894cd351d54328763b1a6819c0953c64857a5d1aae7e8`。Thumb 反汇编以文件偏移 `0x525` 对应运行地址 `0x08020000`。固件和厂商代码留在本机。主机、摄像头及 USB 拓扑的对照见[公司电脑实测](company-pc.md)。

## 佩戴瞬间会启动双路背光

| 触发 | 固件执行顺序 | 现场意义 |
| --- | --- | --- |
| 接近状态变化 | `0x718CD–0x71993` 构造并发送 16 字节的 VCOM 事件 2。小端 `u16` 位于 +12（1 佩戴，0 摘下）和 +14（接近采样值）。成功后在 `0x719AD` 更新状态缓存 | 原厂 Android 的解码也将 +12 的 1/0 各解释为佩戴与摘下。只有心跳的时段也可能是传感器尚未打开 |
| 佩戴 | `0x719B7–0x719D7` 检查佩戴和一个标志位。标志为 0 时调用 `hw_backlight_enable`（`0x7264D`），以当前亮度缓存调用 `set_lcd_backlight_level`（`0x729C5`）。标志非零时清标志并跳过这次背光调用。其后运行 `AudioMute(0)` | 头显收到接近事件后可以自行启用背光并解除音频静音。上报事件和实际执行发生在同一个头显任务内，PCUI 接受开屏命令无法替代这项观测 |
| 摘下 | `0x719ED–0x719F3` 调用 `hw_backlight_disable`（`0x7267D`），将寄存器 2 写 0，然后运行 `AudioMute(1)`。写函数 `0x723F1` 顺序访问两个背光控制器 | 遮挡前后同时涉及背光与音频。仅凭佩戴后掉线无法锁定某一路电源或负载 |
| 设亮度 | `0x729E5–0x72A1B` 接受档位 0 至 4，先保存档位，再根据佩戴状态决定是否写物理背光。FAR 时跳至 `0x72A41`。NEAR 时 `0x7232D` 分别计算两路校准输出，`0x723D3`、`0x723E1` 紧接着写两路寄存器 2 | HID 读回（`0x72A79`）返回已缓存的目标档位。可在 FAR 时保存最低档并读回，再遮挡感应窗。同一条公共亮度路径涉及两路，未识别到独立选择左眼或右眼的普通亮度命令 |

启动描述符 `0xB9E51` 指向 `0xC3CE1` 开始的压缩流，长度 `0x2072`，解到 RAM `0x20000400`。按 `0xB0F7D` 解压，亮度表 `0x20006684` 的五个字节依次为十进制 49、54、58、63、68，初始档位 `0x2000ABBB` 为 4。`0x72337` 以档位索引该表，再结合逐路校准值生成寄存器值。**0 档使用非零校准输入 49；摘下时才走明确的寄存器置零路径。** 表项数值没有电流或占空比单位。之前在 Fold7 上实拍普通线 1 档仍能双眼显示，原厂线 1 档也曾黑屏。[上次亮度对照](../../research/evidence/fold7-original-firmware-retest-20261126.txt)

### 怎样区分背光、DP 桥与音频

- 原厂 HID 的 `SET_LOWPOWER`（report ID `0x0D`，`0x64EA5`；07 号 APK 的 `IoSetLowPower` 位于 ELF VA `0x87A8`）与整个头显的低功耗状态相关。参数 0 经系统 ioctl 生成“摘下、请求睡眠”事件，系统在 `0x78ECB–0x78ED9` 申请睡眠并将上述标志 `0x2004AC84` 置 1；参数 1 在系统处于 5 时申请回到 ready。下一次 NEAR 可清掉该标志、跳过传感任务里的第一次背光写。显示桥任务 `DHM_sample_main` 也读该标志，自己的 Faraway→Near 转换会调用 `0x6D915`（DP/MIPI 唤醒）与 `0x6D775`（视桥状态执行 MIPI FIFO 唤醒复位或重配，随后调用双路背光）。这套接口同时改变多项状态，用它不能区分背光与桥的负载。
- `AT^SETSOURCE=0` 选择手机来源，`AT^SETSOURCE=1` 选择 PC，可用 `AT^GETSOURCE?` 核验。来源字节位于 RAM `0x2000ABB8`。每次接近事件都经 `0x6CEE9` 更新显示桥的 AudioMute。只有来源为 PC，`0x719DB–0x71A03` 还会调用第二个音频回调 `0x5D361`，它也供音频播放任务的 pause 分支使用。因此可在 FAR 下切换来源并读回，在同一原生 90 Hz 信号和原厂线下重复一次遮挡，检验 **PC 独有的第二个回调** 是否是掉线的必要条件。这项对照无法隔离首个 AudioMute 或双路背光。
- 从启动数据重建 AT 命令表后，`AT^EARENABLE` 和 `AT^EARCHECK?` 均指向只作公共应答的 `0x8243F`。工厂命令 `AT^FORCESTARTAUDIO` 的处理器 `0x84B9D` 仅在参数为 1 且内部播放标志为 0 时给音频任务投递初始化消息，参数 0 未停止音频或维持静音。`AT^LCDMODE` 的处理器 `0x8438F` 切换两套双路背光配置；此处没有单眼选择及运行态模式读回。

## 能把掉线前后排进同一时间线的事件

- **独立心跳。** `0x78DAB–0x78DD1` 启动周期为 2000 tick 的定时器；回调 `0x78C37` 向系统队列投入内部消息 7。系统处理分支调用 `0x78C6D`，发送 16 字节的 VCOM **事件 3**。开头为 `01 42 00 00 01 01 10 00 03 00 04 00`，+12 为递增的 32 位小端序号。发送失败会记录错误并返回。这段路径未要求主机回复。在新 PD 电源的现场记录中，COM19 被动接收，每两秒递增一次。内部消息号 7 与线上事件号是两套编号。
- **佩戴与最后的活跃证据。** 11 月 26 日 10:58:27.599–.600（香港时间），同一 COM19 连接收到 `01 42 00 00 01 01 08 00 02 00 04 00 01 00 FF 07`，即 NEAR=1，采样 2047。10:58:27.779 仍收到心跳 78，10:58:28.723 串口读取失败。约 1.12 秒指主机记录佩戴到串口失效的间隔，实际电气中断发生的时刻需要独立测量。不同事件的 +6 字段不能统一当成完整帧长。
- **持续视频中的单变量对照。** 另一次保持同一 90 Hz 原生视频与 PD 电源，FAR 持续至少 176 秒。11:03:14.357 收到心跳 115。11:03:15.287 单独遮挡后出现 NEAR=1，采样 `0x032D`。按节拍应在 11:03:16.357 到达的心跳 116 缺失，11:03:17.788 开始根口重新枚举，COM19 于 11:03:17.793 报读失败。这次掉线与佩戴转换有关，原生视频在未佩戴时已经能够稳定传输。电源、显示桥和音频环节的先后仍需测量。
- **恢复后的心跳复位。** 10:59:24.357 与 11:06:47.258 两次重新打开 COM19 都收到序号 0。计数器 `0x2004AC8C` 处于启动清零区（描述符 `0xB9E31`，起点 `0x2000CFC8`，长度 `0x3DDD8`），直接地址引用仅见 `0x78C7B–0x78C8F` 的取值、自增。这支持头显在恢复过程中重新初始化过。期间的人工重插和主机恢复端口也可能引起重启，不能据此将首次掉线归因于 MCU 主动复位。
- **异常码。** `0x55369–0x553C3` 产生 20 字节的 VCOM 事件 4，+12 的小端 16 位承载当前缓存的系统异常码。启动处分支 `0x555BB–0x555DB` 仅在 RAM `0x2004FFFC` 中的值为 1 至 33 时更新 NV 项 `0x81`，随后总会读取该项并缓存；`0x61D05` 记录 `sys_exce_code`。因此只读异常查询可对照重新枚举前后是否有新值，0 不能排除供电瞬降或未落盘的复位。已检查的代码未把所有复位来源持久化为这一数值。
- **温控告警。** `0x73577` 写入线上事件号 7，`0x7358F–0x73597` 对温度样本分类，把等级写入 +12 的 32 位字段。对于等级 1 或 2，固件比较上次上报等级、检查计数到 4 和其他门限后，才会在 `0x7360D` 发送 16 字节的消息。Android 程序也把 +12 解释为过热等级。一次佩戴后迅速掉线，未收齐告警帧无法排除温控与电气保护。[Android 上行解码](android-cable-analysis.md)

## 头显处理断开与复位的路径

| 观察点 | 固件证据 | 能确定的范围 |
| --- | --- | --- |
| CC1、CC2 | `AT^TYPECSTATE?` 处理器 `0xAB27F` 对 `0xAB745` 的结果加 1。仅 CC1 非零回 1，仅 CC2 非零回 2，两者同时非零或同时为零回 3。控制器初始化失败也可回 3 | 两种插头方向可返回 1、2。同一数字无法说明电压、电流、PD 协议或 DP 视频是否正常 |
| Type-C 脱离 | `0x92999` 记录 `TCPC: usb_port_detached`，`0x929C1` 调用 `0x96731` 将 DP switch 的一组寄存器置回脱离配置。另有状态机日志分别标记 `LC->Detached (PS)`（`0x95507`）和 `LC->Detached (CC)`（`0x955E5`） | 设备端存在区分电源状态和 CC 状态的分支。当前 COM19 只收到对外事件，没有相应底层日志，尚无法指出现场执行的分支 |
| 系统收到 USB Remove | 系统任务从 `0x78E59` 记录 `USB Remove` 和 `VR going to power down`，随后申请系统状态 6。在支持的前置状态下 `0x5DDAD` 清理子系统、启动周期 100 tick 的定时器。其回调 `0x5DD31` 读取逻辑 GPIO 0x18；取值 1 时直接请求系统复位；另一条分支检查计数再执行 GPIO 电源时序 | 已找到软件处理拔除后可以自复位的机制。尚未取得首个拔除事件的来源、触发时电平或现场底层日志，不能把这条路径当作本次故障起点 |
| USB Hub 与 PHY 复位 | 初始化函数 `hw_power_init_phase1`（`0x659BD`）直接调用 `hw_usbhub_reset`（`0x79779`）和 `hw_usbphy_reset`（`0x79A0D`）。Hub 复位脉冲操作逻辑 GPIO 0x19。已扫描的主处理器代码仅在该初始化段找到对这两个入口的直接调用 | 若头显以完整上电流程重新启动，这段代码可连带重置 Hub。代码没有证明主机启用视频或每次佩戴都会调用 Hub 复位 |

Windows 观察到的三只设备是 Hub 后方的音频 `12D1:1092`、控制 `12D1:107E` 与 VIA HID `2109:8888`。普通线成功出图时三者也在。该头显升级镜像与已验证的 PCUI/HID 接口尚未给出 `8888` 的实时 VBUS 电压、电流或锁存故障原因读数。要验证是否由掉压触发，可将眼镜端 VBUS 波形与佩戴、USB 断开时间作对照。要判定 PD 主动切换，可同步记录 CC/PD 协商。只看 GPU 继续报 3200×1600 或单个新心跳不足以区分二者。[接口及既有对照](../cable-firmware-research.md)

## 普通主机能读到哪些掉线记录

华为 VRServiceX 11.0.0.322 的 JNI 库包含 `AT^QUERYEXCEPTION` 和 `AT^PULLMCULOG=LKMSG`，字符串文件偏移分别为 `0x13908`、`0x1391C`。在同一 APK 的 DEX 中，复制 LKMSG（`0xE237E`）和清除异常（`0xE235E`）是独立调用。另一次 Fold7 实测中，原厂线和已出图的普通线均能读到异常码 0，两种线的 LKMSG 请求均返回 `NO PERMISSION`。这条回复来自权限判断，不能据此推断头显上有无日志。[Fold7 原始应答记录](../../research/evidence/fold7-original-firmware-retest-20261126.txt)

| 查询 | .357 的应答与读后行为 | 对掉线的判别力 |
| --- | --- | --- |
| `AT^QUERYEXCEPTION` | `0x61D2D` 将缓存错误码格式化为 ASCII 十进制并发送。读取保留原值。`0x555BB–0x555DB` 在启动暂存码为 1 至 33 时更新非易失项 `0x81`，随后回读该项。独立清除处理器 `0x62335` 才会把该项和缓存写为零 | 能保存一次已走到记录分支的异常。已有非零码可能来自早先运行。连续读 0 仍可发生 USB 脱离或来不及记账的掉电 |
| `AT^PULLMCULOG=LKMSG` | `0x54CF5–0x54D01` 进入 `0x62215`。缓存异常码为 **32 或 33** 时才打开文件，从偏移 0 读取缓存长度的日志并关闭。其他值只在设备内部记录无异常快照。`0x54F45` 分段最多 500 字节，正常完成时发送 20 个 ASCII 竖线。读取函数未清除异常码或删档 | `hi64xx_watchdog_process` 的 `0x5A1B1–0x5A1C7` 先保存音频子系统故障日志，再登记 **32** 并发事件 4。缓存长度在启动清零区，找到的直接写入属于生成快照的流程。即使错误码跨断电保留，尚无证据证明再次冷启动能恢复上次快照的有效长度。33 的具体来源待查 |
| `AT^GETLOGCFG` | `0x54B51–0x54C43` 只读当前打印方式和日志级别，返回文字。sync 模式只打印，nonsync 模式写日志文件。级别 0 关闭，1 错误，2 含警告，3 含信息，4 全部 | 能判断固件是否配置为写入普通日志，不能证明断电前最后一条已经落盘。当前权限下可获得何种响应应以实测为准 |
| 普通 MCU 文件日志 | 固件对 `PULLMCULOG` 的 `=MCULOG` 参数另走 `0x54C55`，按循环文件的起止位置读出。普通读取未调用清除函数。未确认 11.0.0.322 应用实际发送过该参数 | 若主机正常获得日志，可按时间寻找 `LC->Detached (PS)` 和 `LC->Detached (CC)`。两条打印使用同一警告级别，进入文件后台时需至少级别 2（`0x95507`、`0x955E5`、`0xB0949`、`0x629E7`）。系统任务的 `USB Remove` 属于信息级，需要级别 3。缺失其中任一行不能判定首个物理故障 |
