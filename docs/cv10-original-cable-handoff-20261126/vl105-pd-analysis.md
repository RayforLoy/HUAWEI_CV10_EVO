# VL105 两版固件与出流后掉线

2026-11-26，离线比较。**两版都包含一条会主动改变端口寄存器、等待并恢复的控制路径。C9.52.6 还增加了一个独立的延迟脉冲。** 在这根线上，两版都曾收到头显开屏成功应答，随后失去头显 USB。当前没有抓到哪条固件路径在故障时实际执行。公司 PC 推迟启用视频后控制接口能维持约 159 秒；另一次开始 90 Hz 视频后约 2.05 秒，集线器端口 1、2、5 同时报告无设备。故障时间应从**出流和电气事件分别计时**。[PC 事件记录](company-pc.md) · [两版 Fold7 实测](../../research/evidence/fold7-original-firmware-retest-20261126.txt)

## 输入和地址约定

两份文件均为 49,152 字节。C9.49.6 样本 `firmware_update/firmware/cable/stock/CV10-cable-C9.49.6.bin` 的 SHA-256 为 `f16057065c4c29d6d86901239371f2a6aab2bcf03c6976505c8f5971fba93e02`，与 `CV10-cable-20261125-210954.bin` 相同。C9.52.6 样本 `firmware_update/firmware/cable/stock/CV10-cable-C9.52.6.bin` 为 `1ebf1217d0dda526f64ed3b15504db409fbdf25bc866f0fbebb874adcd00485a`。文件 `0x1003` 起分别为 `0C 09 49 06`、`0C 09 52 06`。复核使用 pypcode 4.1.0 的 Ghidra SLEIGH `8051:BE:16:default`，代码起始地址 0。下文将裸文件指令地址、内部间接 RAM 和 MOVX 访问的 XDATA 分开。相同 XDATA 数值在两个构建中可能对应不同变量。

### 新版的 1000 计数到期后有实际动作

1. `A337–A35A` 在 XDATA[2A5B] 为 1、内部直接 RAM[46] 为 17h、间接 RAM[89] 为 86h、XDATA[2BEB] 为 0 时，将状态从 1 改为 2，并向 2BEB 写入 0Ah。随后 `0E85` 或 `5453` 两个调用点可将状态从 2 改为 4。`4BC2` 的 11 字节为 `78 D2 76 03 08 76 E8 74 04 F0 22`，设置间接 RAM[D2:D3] 为 03E8h（1000）。
2. 中断向量 `002B` 转到 `8C23`。`8C4B–8C79` 遍历两组各八个 16 位倒计数，非零时减一。`A363–A36B` 调用 `96CB`，带入端口 1、槽 6，索引为 `B6h + 10h + 2×6 = D2h`。它检查的正是先前装入的同一对字节。1000 因此是**软计数中断次数**，没有时钟标定，不能直接换算为毫秒。这一槽在 `310E` 附近也可被设置为 2000 或 500，单凭文件有 2000 常量同样无法解释实测约两秒。
3. 状态 4 且计数归零后，`A36D–A3A5` 清状态，`A376` 写 XDATA[1201]=F0h，随后明确对端口 1 的 XDATA[0003] bit 3 置位、等待、清位。和共有路径的 5 个事件不同，这里传给 `97F3` 的参数是 20。`9A7A` 每次把 TL0/TH0 装为 20h/F8h 并启动；向量 `000B` 对应的 `9A85` 中断置完成标志。之后固件调用端口状态清理函数并将 XDATA[0003] bit 0 置 1。读回版 C9.49.6 没有在相同分支条件下通向这条完整链的证据。它已有上一节的寄存器脉冲，因此仅观察一次 USB 重枚举不能区分两条路径。

## 从实机身份字节识别充电芯片

C9.49.6 在 `0xA193–0xA19C` 从板内 I²C 地址 `0x53` 的寄存器 `0x0B` 读取一个字节，存入 `2E00`。先前在这根线单接电脑时取得 35 份样本，加辅助 5 V 后取得 96 份，均为 `0x69`。立锜驱动把该寄存器定义为 INFO，位 6 至 3 的值是 `(0x69 >> 3) & 0x0F = 0x0D`，对应 **RT9471**。驱动为 RT9471D 定义了不同的 ID。C9.49.6 在 `0x8F4A` 处的一组六字节配置也与立锜驱动中的完整序列相符。这是电子身份与固件行为的交叉识别；还没有板上芯片丝印照片。[本线原始样本](../../research/evidence/fold7-original-firmware-retest-20261126.txt) · [上游型号识别](https://github.com/torvalds/linux/blob/4dd10fbbeb9c33709edc89916e19c03c780a0751/drivers/power/supply/rt9471.c) · [立锜驱动的同一序列](https://android.googlesource.com/kernel/google-modules/bms/+/0dc346205b6bd3fdc5a963df1ceffb625eae001e/rt9471_charger.c#877)

| 线控数据或操作 | 可以推断的行为 |
| --- | --- |
| `0x55:2C` 返回的电量字节为 `FF` | `0xA1C8–0xA1EB` 把 255 按大于 60 处理。若当时 RT9471 的 FUNCTION 寄存器位 0（`CHG_EN`）为 1，则清掉该位。小于 40 时走允许充电的分支。读取函数直接返回 I²C 接收值；仅凭 FF 无法判定板上电量计是否应答，也不能当作实际电量。线控还有整字节写 FUNCTION 的其他路径，无法由这份快照推断充电始终关闭。 |
| 温度字为 `FFFF` | `0xA154–0xA15F` 遇到 `FFFF` 或 `0000` 会跳过这一次温度比较。RT9471 自身仍有独立温度状态，不能从这两字节推断实际温度。 |
| `2DFF` 随辅助供电从 `81` 变为 `83` | `0xADC2` 初始化这个 VL105 端口状态字；索引 1 的事件可以改变位 1。这个位置没有保存 RT9471 FUNCTION。该变化无法证明充电、升压或电池开关动作。 |
| 线控在保护状态下写 FUNCTION | `0x81DE–0x81F1` 检查 RT9471 的温度调节状态及电池高温状态，相关支路可进入状态 `A1`。在特定计时条件满足后，`0x824D–0x825C` 的写入包含 `BATFET_DIS`。其他状态也可写该位。检测到这个程序分支只说明线盒有控制电池通路的能力，现场未捕获带载时的实际寄存器值。 |

充电使能、电池隔离和 OTG 升压是三个不同的位。厂家还列出 VBUS 新接入可解除运输模式，电池输出过载也可能使芯片自行隔离电池。线盒辅助插口到具体芯片引脚的走线尚未核实。要验证电池通路是否参与故障，可先对工作正常的同型号线读取电量与原始温度；要定位佩戴瞬间的第一处电气变化，仍需在同一时间轴上观测眼镜端 VBUS 与 CC/PD。[RT9471/D 数据手册，第 23 页及 FUNCTION 寄存器](https://www.richtek.com/content/dam/richtek/data/en/resources/product-specifications/rt94/rt9471-rt9471d/product-data-sheets/pdf/DS9471D-04.pdf)

### Windows 带载结果

本线接同一电脑口与独立 5 V / 2 A 电源。11 秒的空载窗口起止均为 `A0`。重新开始采集后，接上 CV10，头显实际报告「未佩戴」，Windows 随后向它独立输出 3200×1600、90 Hz 的测试图。14:55:32.702 收到「已佩戴」，开屏命令读回空应答；14:55:32.711 首次读控制口失败，14:55:32.717 主机记录集线器及下挂设备消失。右眼在测试图就绪至录像结束共录得 1,655 帧，没有可辨认的右眼箭头或交替色场。佩戴后第一帧距事件 27 ms。[右眼画面](../../research/evidence/pc-original-port-trace-right-20261126.jpg)
